# AEG 项目评审与功能路线图

审阅日期：2026-11-23（北京时间）
代码基线：`development` 分支，提交 `5a3ff05`。
用途：供产品、运营、报关和研发一起排期。依据为仓库静态审阅及既有故障记录。优先级、工作量和收益均为建议，未使用生产监控或用户行为数据验证。

## 1. 项目现状

主流程是客户或运营上传 Excel → 预览、校验和补全 NCM → 生成报价 → DI 与 DDP 核算 → 报关审核、运营成交跟进 → 物流与文件交付。现有代码支持这条链路的主要操作。本轮优先提高报价正确性和故障恢复能力，再补齐客户决策与通知。

| 范围 | 已有能力 | 部分实现或仍待补齐 |
|---|---|---|
| [客户端](../apps/web-client/src/App.tsx) | 官网与询价入口、报价工作台、报价详情、CNPJ、帮助与个人中心 | 报价专属的客户确认、消息收件箱、结构化补件入口待补齐 |
| [运营端](../apps/web-ops/src/App.tsx) | 报价上传与产品编辑、费率、成交、销售名下客户、物流、财务 | AI 结果可部分回填，跨重启恢复和任务级重试待补齐。成交统计已有基础，完整漏斗待补齐 |
| [报关端](../apps/web-customs/src/App.tsx) | 订单、批量产品编辑、CNPJ、DI 分析与复核、清关进度 | 单证类型、缺件及补交形成统一清单后，可与复核流程联动 |
| [管理端](../apps/web-admin/src/App.tsx) | 仪表盘、客户和员工、模板、模型配置、内容、审计、版本 | 模型任务故障统计、会话撤销和发布健康检查待补齐 |
| [API 与数据](../apps/api/src/app.module.ts) | NestJS 模块，TypeORM/PostgreSQL 与迁移，本地默认 JSON mock。报价、DI、财务、物流等均有接口 | 同一业务同时依赖 mock 与 PostgreSQL 实现，需补关键仓储契约测试与 PostgreSQL 集成回归 |
| [共享组件](../packages/web-shared/src)与[部署](../deploy/hostinger/update.sh) | 共享登录、文件、错误和双语工具。pnpm/Turbo 构建，Hostinger 上经 Nginx、PM2 发布，四端静态文件使用同一个发布链接切换 | API 与静态文件分步骤切换。基线未找到已提交的 GitHub Actions 工作流或常规自动化测试文件，已有[手工用例](./AEG-测试用例.md)可用于提取用例 |

几个旧结论需要更新：

- [登录入口](../apps/api/src/auth/auth.controller.ts)已接入 hCaptcha。登录速率、账户停用后的会话失效和角色隔离应分别验收。
- [发布脚本](../deploy/hostinger/update.sh)已支持整批切换前端。发布一致性应检查线上 API 版本与实际加载的静态资源，不能只根据版本页面或构建缓存的输出判断。
- [报价上传服务](../apps/api/src/upload/quote.service.ts)已把美元金额校验放在换汇前，并按产品行关联复用的 Excel 图片。[AI 服务](../apps/api/src/order/ai-ncm.service.ts)已支持中国十位编码转换及 HTTP 402 提示。优先为这些能力补回归。

## 2. 优先级与建议排期

优先级按业务影响、故障恢复成本及前置依赖排序。P0 处理报价中断、数据正确性和发布风险。P1 补齐从报价到交付的协作。P2 扩展经营管理。工作量为研发及联调的粗估，单位为人日，待拆分后复核。

| 排序 | 建议与代码依据 | 理由与预期收益 | 影响范围 | 工作量与依赖 |
|---|---|---|---|---|
| **P0 · 1** | **报价自动回归与 CI。** 从[上传服务](../apps/api/src/upload/quote.service.ts)、[DI 计算](../apps/api/src/order/di-calculation.ts)及[手工用例](./AEG-测试用例.md)提取稳定样例。CI 执行类型检查、四端构建、计算测试及 PostgreSQL 集成测试 | 在合并前发现报价规则、权限与仓储语义回归，降低本地通过而部署后出错的概率 | API、四端构建、重点覆盖客户端与运营端、GitHub CI | 4–7 人日。准备脱敏 Excel、角色样例和临时 PostgreSQL，模型响应使用可控样例 |
| **P0 · 2** | **可恢复的 AI 与 DI 任务。** 在[AI NCM 服务](../apps/api/src/order/ai-ncm.service.ts)和[报价服务](../apps/api/src/upload/quote.service.ts)基础上持久化任务、输入版本、行级结果及错误分类。页面可查询进度和重试失败行 | 刷新、超时及服务重启时保留已完成成果。HTTP 402 明确指向计费问题，账户恢复前停止自动重试 | 客户端、运营端、报关端 DI、API、模型配置与审计 | 8–14 人日。依赖第 1 项回归基线，并与第 4 项共用版本检查和防重规则 |
| **P0 · 3** | **发布验收、回滚与恢复。** 从[发布脚本](../deploy/hostinger/update.sh)增加提交号、API 健康、四端页面及入口静态资源验证。归档可配对的 API 与前端产物，演练数据库和上传附件的成套备份恢复 | 缩短发现发布异常的时间，明确故障时可恢复到哪个版本和哪份数据 | Hostinger、Nginx、PM2、PostgreSQL、上传附件 | 4–7 人日。依赖可恢复的备份目标、隔离演练环境及兼容迁移方案 |
| **P0 · 4** | **报价确认与核算防重。** [草稿确认](../apps/api/src/upload/quote.service.ts)已有已确认重放处理和进程内防重，补 PostgreSQL 事务和持久化唯一约束，核算写回检查报价版本 | 避免响应丢失、重启或并发提交时创建重复报价，减少旧核算结果覆盖新报价 | 客户端、运营端、上传 API、报价及草稿仓储、迁移 | 5–9 人日。依赖第 1 项 PostgreSQL 回归，实施前核查历史草稿关联 |
| **P1 · 5** | **报价版本、有效期与客户在线确认。** 在[客户端报价接口](../apps/api/src/order/client-order.controller.ts)和[成交统计](../apps/api/src/order/deals.controller.ts)基础上，增加客户对有效发布版本的接受或拒绝。保存币种、汇率、费用快照及确认人和时间 | 减少人工追问，明确客户实际接受的报价条款，区分客户决策与运营记录 | 客户端、运营端、报价数据、版本审计 | 5–9 人日。依赖第 4 项，并复用[在线接受报价实施计划](./AEG-客户在线接受报价实施计划.md)的快照、归属和幂等设计 |
| **P1 · 6** | **客户通知中心。** 从报价发布、客户确认、物流异常和单证待补生成站内消息，提供未读状态、详情跳转与事件去重 | 减少客户反复刷新查询，帮助运营追踪待办并验证触达是否有效 | 客户端收件箱、运营端业务事件、通知 API 与偏好 | 6–10 人日。依赖对应业务事件，复用[客户通知中心实施计划](./AEG-客户通知中心实施计划.md)的事件、双语和去重设计。旧方案从邮件起步，此路线图先上线站内消息，邮件根据数据另行排期 |
| **P1 · 7** | **单证清单与补件。** 在[订单附件接口](../apps/api/src/order/order-files.controller.ts)及[报关复核](../apps/api/src/customs/customs.controller.ts)上增加单证类型、审核状态、原因和版本记录 | 客户能看清缺什么、为什么被退回。运营与报关共用进度，减少重复核对 | 客户端、运营端、报关端、附件与角色权限 | 6–10 人日。产品与报关先确认必需单证和审核角色。上传复用现有文件能力 |
| **P1 · 8** | **物流位置与异常跟进。** 在[运营物流接口](../apps/api/src/order/ops-order.controller.ts)及[AIS 采集](../apps/api/src/order/ais-stream.service.ts)上展示位置来源、更新时间、计划与实际时间，支持带审计的节点修正 | 减少把过期位置或计划时间误读为实时进展。异常有责任人和处理记录 | 客户端、运营端、物流节点、AIS 与地图 | 5–8 人日。运营确认异常类型、位置过期阈值和节点修正权限 |
| **P1 · 9** | **登录与员工会话治理。** 在[hCaptcha 登录](../apps/api/src/auth/auth.controller.ts)和[员工管理](../apps/api/src/staff/staff.controller.ts)基础上增加登录频率控制、停用后的会话撤销及角色回归 | 缩短员工停用后已有会话可用的时间，减少认证与角色管理遗漏 | 四端登录、认证 API、员工管理与审计 | 4–7 人日。依赖角色测试样例与会话迁移安排 |
| **P2 · 10** | **财务对账、询盘分配和运营指标。** 扩展现有[付款登记](../apps/api/src/finance/finance.controller.ts)、[询价入口](../apps/api/src/inquiry/inquiry.controller.ts)和成交统计。先记录收款匹配、询盘负责人和阶段时间，再生成漏斗 | 提高账款可追溯性，减少询盘遗漏，使转化差异能追到具体阶段 | 运营端、管理端、财务、销售、询盘与报表 | 10–18 人日。依赖财务定义对账口径、销售定义分配规则，以及第 5 项提供的客户确认数据 |

## 3. 验收条件

1. **自动回归**：六位 HS、十位中国编码和既有八位巴西 NCM 分别处理。模型返回前缀不匹配时保留原值。美元金额 `902.82` 对重算值 `902.816` 按原币通过，同一图片引用的十个产品行均有正确关联。运行客户归属、销售、运营、报关与管理员权限用例，并通过 PostgreSQL 集成测试。
2. **AI 任务**：模拟一组成功、一组超时、一个 HTTP 402、服务重启及旧版本结果回写。成功行保留，只重试失败行。旧任务结果不能覆盖已修改的商品数据。
3. **发布恢复**：模拟 API 或静态资源验收失败，按流程恢复到可兼容的一对前后端版本。在隔离环境中从同一批备份恢复订单及对应附件，记录恢复耗时。数据库迁移逐项确认向后兼容，涉及破坏性迁移时单列恢复步骤。
4. **并发确认**：同时提交同一份草稿、超时后重放及进程重启后重试，最终均指向同一个报价。旧版本核算结果被拒绝或明确要求重新核算。
5. **客户确认**：客户能对归属自己的有效报价版本接受或拒绝。重复同一决策返回已有结果，过期或被替代的版本拒绝确认。运营端可追溯当时的费用与币种。
6. **客户通知**：重复业务事件只产生一条相同消息。客户可查看自己的未读消息、标已读并跳转。中葡文案、跨客户隔离及事件失败后的补偿可验证。
7. **单证补交**：指定角色可标记缺件和退回原因。客户补交后保留历史版本，报关可查看当前待复核附件。跨客户下载或越权审核被拒绝。
8. **物流异常**：分别验证正常 AIS、陈旧位置、无数据及人工修正。来源和更新时间可辨，节点修正可追溯。
9. **会话治理**：验证正常登录、人机验证失败、连续失败、角色访问与停用员工的旧会话失效。客户与员工的既有正常登录流程通过。
10. **经营管理**：验证一笔付款从登记、匹配到差异处理，一条询盘从进入、分派到成交或失单。报表数字可追溯到原始事件，币种与时间范围一致。

## 4. 上线顺序与衡量

- **第一阶段**：先建立第 1 项回归基线，同时做第 3 项的发布验证。第 4 项明确数据写入约束后，接入第 2 项的版本检查与恢复规则。
- **第二阶段**：先上线报价版本与客户确认，再逐步加入站内通知。单证与物流的消息随业务事件上线。会话治理可与这批并行。
- **第三阶段**：采集数据后补齐财务对账、询盘分配与漏斗。共享组件进一步收敛、列表索引、任务运行环境和附件存储扩展，依据实际重复维护成本、查询耗时及恢复目标另行排序。

| 指标 | 采集口径 |
|---|---|
| 报价确认失败率 | 失败的确认请求 ÷ 全部确认请求。区分用户校验、外部服务与系统错误 |
| AI 失败行重试成功率 | 重试后得到可接受结果的行 ÷ 已执行重试的失败行。按超时、计费和匹配失败分组 |
| 发布与恢复质量 | 记录发布验收失败次数、回滚耗时，以及演练中订单与附件的恢复成功率 |
| 客户决策效率 | 从报价版本发布到该版本首次有效决策的中位时长，另记在有效期内的决策比例 |
| 通知与协作 | 按事件查看已读率、待补件完成时长及物流异常处理时长 |

上线前先建立基线。观察口径稳定后再定量化目标，避免把预期收益当成已取得的结果。
