# AEG DDP 系统 —— 功能建议与优化规划

整理日期：2026-11-17
分析对象：`aeg` 仓库当前工作区代码（api + 四端前端 + 4 个 packages）
分析方式：通读代码结构、实体与迁移、核心控制器、四端路由与部署脚本；本文所有判断都标注了代码依据
配套文档：`docs/四端产品需求文档.md`（能力现状）、`docs/AEG-测试用例.md`（手工用例）

---

## 一、结论摘要

**现状判断：业务主干已经跑通，短板不在"缺功能"，而在三处结构性缺口。**

1. **客户侧没有触达与回传。** 报价好了、船开了、文件传了，客户不会收到任何通知；客户也无法在线接受或拒绝报价——`deal_status` 完全由运营手工填写。这让"成交"是运营的推测，不是客户的确认。
2. **工程侧没有护栏。** 全仓库 **0 个自动化测试、0 个 CI 配置**；数据层同时存在 JSON mock 与 PostgreSQL 两套实现（`mock-db.ts` 1445 行 + `pg-repos.ts` 688 行），靠人工保证语义一致。任何一次改动都缺少回归保护。
3. **运行侧是单机假设。** 上传文件、AIS 轨迹、登录限流计数器全在本地磁盘或进程内存，定时任务在每个实例都会跑。当前单 VPS 没问题，一旦扩容或迁移就会出问题。

**建议的优先级前五项（详见第六节）**

| 序 | 事项 | 类型 | 理由 |
|---|---|---|---|
| 1 | 测试骨架 + CI（类型检查/测试/构建） | 技术 | 后续所有改动的安全网，成本最低收益最高 |
| 2 | 客户通知（邮件）+ 报价单 PDF | 业务 | 直接影响成交效率，是报价系统的"最后一公里" |
| 3 | 客户在线接受/拒绝报价 | 业务 | 让成交数据变成事实而非推测 |
| 4 | 数据层双轨收敛 | 技术 | 消除"本地通、线上不通"这类最难排查的问题 |
| 5 | 登录限流 + 密码策略 + CORS 白名单 | 安全 | 当前登录接口无任何频率限制，生产可被暴力破解 |

## 二、项目现状

### 2.1 技术栈与规模

| 项 | 现状 |
|---|---|
| 后端 | NestJS + TypeORM + PostgreSQL（`APP_MODULE_MODE=postgres`）／本地默认 JSON mock |
| 前端 | React 18 + Vite + react-router + zustand + i18next，四端独立构建 |
| 移动端 | `web-ops` 已接 Capacitor（`apps/web-ops/capacitor.config.ts`），有 `android/` 工程 |
| 构建 | pnpm workspace + turbo |
| 代码量 | 约 **17,090 行** TS/TSX（不含 dist/node_modules），其中 api 约 1.3 万行 |
| 数据模型 | 17 个实体、**26 个迁移**；报价单把 `pricing_breakdown`、`shipment`、`di_analysis`、`customs_review` 都放在 `quote_order` 的 jsonb 列里 |
| 测试 | **0 个** `*.spec.ts` / `*.test.ts` |
| CI/CD | **无** `.github`；部署靠 `deploy/hostinger/update.sh` + release 目录 + current 软链 |

### 2.3 值得肯定的设计

这些是后续改动应当**保持**的既有资产，不是建议项：

- **状态机有显式约束**：`STATUS_TRANSITIONS` 校验报价状态流转，非法跳转直接拒绝（`ops-order.controller.ts:307-322`）。
- **权限双层**：`AuthGuard` + `RolesGuard` + `ClientScopeInterceptor` 三层；客户侧文件下载有归属校验（`order-files.controller.ts:170-176`）。
- **生产密钥强校验**：`NODE_ENV=production` 且未设 `JWT_SECRET` 时**拒绝启动**（`main.ts:8-11`），这点很多项目做不到。
- **双语文案完整覆盖**：运营端 zh/pt 各 738 条、客户端各 656 条，数量完全对齐，没有半成品翻译。
- **外部依赖有降级**：汇率接 ECB（Frankfurter），上游失败返回过期缓存并标 `stale`（`fx.controller.ts`）；AI 识别有配置档案与超时。
- **审计有落点**：`ops-order.controller.ts` 内 9 处写审计，覆盖删除、状态、费用、DI、物流节点、文件。

## 三、现状诊断：风险清单

按"会不会真出事"排序，每条附代码依据。

| # | 风险 | 依据 | 后果 |
|---|---|---|---|
| R1 | **无自动化测试、无 CI** | 仓库无测试文件、无 `.github` | 改动靠人工回归，重构不敢动；已出现过"本地编译通过、线上跑旧进程"的发布问题 |
| R2 | **数据层双轨** | `common/mock-db.ts`(1445) 与 `common/pg-repos.ts`(688) 实现两套仓储 | 语义漂移：本地 JSON 通过、Postgres 报错，或排序/空值行为不同 |
| R3 | **登录无频率限制** | 依赖列表无 `@nestjs/throttler`，全仓库无 `Throttle` | 可对 `/api/auth/login` 暴力破解；密码最短仅 6 位（`password-policy.ts`） |
| R4 | **CORS 默认全开** | `main.ts:34` 未配 `CORS_ORIGIN` 时 `origin: '*'` | 生产若漏配环境变量，任意站点可带 Cookie 调接口 |
| R5 | **令牌不可撤销** | JWT `expiresIn: 12h`，无 refresh、无黑名单（`auth.module.ts:14`） | 员工离职后令牌仍有效 12 小时；无法"踢下线" |
| R6 | **单机状态** | AIS 轨迹在内存 + `data/ais-tracks.json`；定时扫描用进程内 `setInterval`；上传文件存 `apps/api/uploads/` 本地磁盘 | 扩容即重复订阅/重复扫描；迁移丢轨迹；磁盘满则上传全挂 |
| R7 | **迁移时间戳冲突** | `1762300000000-CnpjRegistrySnapshot.ts` 与 `1762300000000-DiReviewVersions.ts` 同号 | TypeORM 按"时间戳+文件名"排序才勉强有序，新增迁移极易排错顺序 |
| R8 | **列表查询索引不全** | 迁移只建了 `client_id` / `salesperson_id` / `status` 单列索引，`deal_status` 无索引 | 数据量上万后，"成交/未成交"筛选走全表扫 |
| R9 | **发布不一致（已发生）** | `versions.json`：api/ops/client 为 `ab346cc`（11-16），admin/customs 停在 `eef1d24`（11-13） | 四端版本不同步，前端调后端新接口会 404 |
| R10 | **无监控无错误上报** | 全仓库只有 `console.log`/Nest `Logger`，无 `/health` 探针 | 线上故障靠用户反馈；重启后无法判断是否恢复 |
| R11 | **mock 全量同步写盘** | `mock-db.ts:458` `fs.writeFileSync` 每次变更写整个 876KB JSON | 本地并发时卡顿、可能写坏文件（仅开发环境，影响有限） |
| R12 | **共享层几乎为空** | `packages/web-shared` 仅 193 行；`ShipmentRouteMap` 等组件靠手工复制同步 | 两端 UI/逻辑漂移，改一处漏一处（已人工同步过多次） |

## 四、功能建议

编号 `F-x`；成本口径：S ≤ 3 人日、M ≈ 1-2 周、L ≥ 3 周。

### F-1 客户通知中心（邮件 / 可选 WhatsApp）　`P1`　`M`

**问题**：客户提交资料后，报价完成、节点更新、文件上传**都没有任何通知**。客户只能自己反复登录查看。运输类业务里，这条链路通常靠微信/WhatsApp 人工同步，成本高且易漏。

**建议**：
- 新增 `NotificationModule`：事件源挂在三处——报价核算完成（`status: done`）、物流节点新增、交付文件上传。
- 邮件模板中葡双语（复用现有 i18n 词条口径），支持"每日摘要"与"即时通知"两档，避免邮件轰炸。
- 表 `notification_log` 记录发送状态，失败可重试；客户端"个人中心"增加通知偏好开关。
- WhatsApp 走第三方 BSP（如 Twilio/Meta Cloud API），建议二期再上，先做邮件。

**收益**：客户回访率与成交率直接提升；运营不再需要手工"通知客户"，单人可服务的订单量上升。
**影响范围**：api 新增模块 + 3 处事件埋点 + 两张表；client 端偏好页；admin 端可选发送日志页。

### F-2 报价单 PDF 导出与留档　`P1`　`M`

**问题**：系统是报价系统，但**没有任何 PDF 生成能力**（全仓库无 pdfkit/puppeteer/pdf-lib），报价只能登录后在页面看。而外贸场景里，客户要把报价单转给老板/财务/报关行，标准载体就是 PDF。

**建议**：
- 服务端生成 A4 报价单：公司抬头、报价号、有效期、费用明细、汇率与生成时间、免责声明。
- 运营端"下载 PDF"；客户端详情"下载 PDF"；文件落 `order_file` 表并记版本（价格改动后重新生成，旧版留档）。
- 同时导出 Excel 版给客户自己算（复用 `packages/excel-utils`）。

**收益**：报价可直接对外流转，不再靠截图；价格版本可追溯，减少"客户说当时报价不是这个数"的争议。
**影响范围**：api 新增 `pdf` 服务（建议 puppeteer 复用前端模板，样式最可控）+ 2 个端点；两端各 1 个按钮；`order_file` kind 增加 `quotation`。

### F-3 客户在线接受 / 拒绝报价　`P1`　`S`

**问题**：`client-order.controller.ts` 对报价**唯一的写操作是 `@Delete(':id')`**（第 15 行）。`deal_status` 只有运营能改，意味着"成交"是运营听到电话后手工回填的推测，不是客户的确认。转化漏斗的数据因此不可信。

**建议**：
- 客户端详情页增加"接受报价 / 不接受（必填原因）"两个动作：`POST /api/client/orders/:id/decision`。
- 接受 → `deal_status='won'` + `deal_closed_at` + 记 `accepted_via='client'`；拒绝 → 记录原因，保留在详情里供运营复盘。
- 运营端展示"客户已于 X 时间在线确认"，与手工标记区分；覆盖前需二次确认。
- 状态变更写审计（沿用现有 `auditRepo.entry`）。

**收益**：成交数据变成事实；运营不必逐单电话确认；拒绝原因沉淀成可分析的产品/价格反馈。
**影响范围**：client 接口 + 详情页；ops 详情展示；审计。

### F-4 物流节点编辑（PATCH）　`P1`　`S`

**问题**：节点只能新增和删除。时间录错、备注写错，只能删了重加——审计日志里会留下"删除 + 新增"两条噪音，且时间线顺序可能错乱。

**建议**：`PATCH /api/ops/orders/:id/shipment/events/:eventId`，允许改 `happened_at` / `note` / `lat` / `lng`，写审计记录"改前→改后"。前端时间线每条加编辑按钮。

**收益**：运营可修正而不破坏轨迹；审计更可读。
**影响范围**：1 个接口 + ops 详情时间线；client 只读，无需改。

### F-5 物流阶段扩展：中转港 / 运河 / 异常　`P2`　`M`

**问题**：`SHIPMENT_STAGES` 只有 10 个阶段，海上段**只有 `on_water` 一个**，实际靠备注区分"过马六甲""好望角"。客户端看到一个没有语义的点。

**建议**：新增 `transshipment`（中转港，可落具体港口坐标）、`canal`（运河通过）、`rolled`/`rebooked`（甩柜/改配，异常类）。同步改：`port-geo.ts` 落港规则、`sea-route.ts` 插值、四端词条、清关端展示。

**收益**：轨迹有业务语义；异常节点（甩柜）可以被统计，而不是埋在备注里。
**影响范围**：后端枚举 + 定位规则；ops/client/customs 词条与时间线；约 6 个文件。

### F-6 单证清单与缺件提醒　`P1`　`M`

**问题**：交付文件只有 `clearance_shot / invoice / other` 三类自由上传（`order-files.controller.ts:22`），没有"这票应该交哪些单"的清单概念。漏发提单或发票，往往到清关才被发现。

**建议**：按航线/贸易条款配置单证清单（提单、发票、装箱单、原产地证、放行截图……），每票生成 checklist；已上传自动勾选；缺件在运营端列表和客户端详情显示黄条提示。

**收益**：把"靠人记"变成"系统催"，减少清关卡货；新人也知道这票该收什么单。
**影响范围**：`order_file.kind` 扩展或新增 `order_document_checklist` 表；ops/customs/client 三端展示。

### F-7 CNPJ 额度使用明细与预警　`P2`　`M`

**问题**：`customs-cnpj` 有额度字段（含 `quota_usd`），但没有"已用/剩余"的逐笔明细，也没有临近阈值提醒。超额申报会直接卡关。

**建议**：额度消耗按 `di_analysis` 逐票累计，提供"已用/剩余/预计耗尽时间"；剩余低于阈值时在清关端首页告警，并在新 DI 提交时前置校验。

**收益**：避免临柜才发现额度不够；额度使用可审计。
**影响范围**：customs 模块 + cnpj 表增加汇总；customs 首页与详情。

### F-8 财务：账龄、对账与逾期提醒　`P2`　`M`

**问题**：`finance.controller.ts` 只有 `receivables` / `payments` / `summary` 三个读取与写入点，没有账龄分档、没有对账单导出、没有逾期提醒。`payment_record` 有数据但没被充分使用。

**建议**：应收按 0-30/31-60/61-90/90+ 分档；按客户导出对账单（PDF/Excel）；逾期自动进 F-1 的通知队列。

**收益**：现金流可见；催收有依据。
**影响范围**：finance 模块为主；ops 财务页；依赖 F-1 与 F-2 的导出/通知能力。

### F-9 汇率快照与汇兑损益　`P2`　`S`

**问题**：汇率是实时查询（6 小时内存缓存），`pricing_breakdown.fx_rate` 已存快照（这点做对了），但没有"报价汇率 vs 收款汇率"的对比，跨月波动对本币利润的影响看不见。

**建议**：报价生成时固化 `fx_rate_snapshot` + 来源与时间；收款时用当日汇率折算，差额单独计"汇兑损益"列；财务页展示本月损益。

**收益**：毛利口径准确；定价时知道自己承担多少汇率风险。
**影响范围**：finance + pricing；ops 财务页。

### F-10 运营看板：转化漏斗与毛利　`P2`　`M`

**问题**：`admin-stats` 只有一个 `overview`；运营端 `deals` 有基础统计。缺"上传→核算→报价→成交"的漏斗和按业务员/航线的毛利排名。

**建议**：漏斗按状态与时间窗口统计；毛利取 `pricing_breakdown.profit_brl` 聚合；支持按业务员、客户、航线、月份切片。

**收益**：管理决策从"感觉"到"数字"；能定位是哪一环掉客户。
**影响范围**：admin/ops 各一个看板页；后端 1 个聚合接口（注意加索引，见 R8）。

### F-11 官网询盘线索落库　`P2`　`S`

**问题**：`inquiry.controller.ts` 是纯 AI 对话，**对话内容不落库**（`visits` Map 只做限流）。官网流量来了又走，线索零沉淀。

**建议**：对话结束或用户留联系方式时落 `inquiry_lead`（公司、货物、起运地、目的地、联系方式、对话摘要）；管理端可查看、分配给业务员；与 `client` 建档打通。

**收益**：把官网从"展示页"变成"获客入口"，是当前最低成本的增量来源。
**影响范围**：inquiry 模块 + 1 张表；client 官网表单小改；admin 新增线索页。

### F-12 员工账号治理　`P1`　`S`

**问题**：**没有"管理员重置员工密码"的接口**（`auth.controller.ts` 只有登录/注册；`client.controller.ts` 的改密只针对客户）。销售忘记密码只能改库。同时无法强制下线、无法查看在线会话。

**建议**：`PATCH /api/admin/staff/:id/password` + 管理端按钮；用户表加 `token_version`，改密/停用时自增，旧令牌立即失效（低成本版"踢下线"）。

**收益**：账号运维不再动数据库；离职场景可控。
**影响范围**：staff/auth 模块 + 管理端员工页 + JWT 校验读 `token_version`。

### F-13 AIS 商业卫星源接入　`P2`　`L`（按需）

**问题**（已实测）：AISStream 免费层是岸基汇总，南海中部、南印度洋、南大西洋中部 **20 秒内 0 条报文**；单船几分钟到十几分钟一个点。跨洋十几天在图上就是空白。

**建议**：保留 AISStream 做近岸补充；跨洋段接商业源（MarineTraffic / Datalastic / Spire），按 MMSI 直查 + 卫星覆盖，按查询次数计费。接入前先做成本测算（单票航程 × 查询频率 × 单价）。

**收益**：客户随时能看到船在哪个洋区，而不是"十几天没动静"。
**影响范围**：`ais-stream.service.ts` 抽象成 Provider 接口；新增计费与配额控制；地图无需改。

### F-14 移动端补全：推送与拍照上传　`P2`　`M`

**问题**：`web-ops` 已有 Capacitor + `android/` 工程，但缺推送、拍照上传、离线草稿——而港口/仓库现场恰恰是这些场景。

**建议**：接 FCM 推送（节点变更、新订单）；拍照直接上传 `order_file`；弱网下草稿本地暂存。

**收益**：现场人员不必回办公室录数据，节点时效性提升。
**影响范围**：web-ops 移动端 + 后端推送 token 表。

## 五、技术优化

### T-1 数据层双轨收敛　`P0`　`L`

**问题**：`mock-db.ts`(1445 行) 与 `pg-repos.ts`(688 行) 是两套仓储实现，语义一致性全靠人工。这类问题最阴险：本地一切正常，上线才暴露排序、空值、事务差异。

**建议**：本地也跑真 Postgres（Docker Compose 已有 `deploy/docker-compose.yml`，改造成 dev 用）；mock 仅保留 seed 与离线演示开关，所有业务路径统一走 Repository。分两步：先让 CI 在 Postgres 上跑集成测试，再逐模块删 mock 分支。

**收益**：消除一整类"环境相关 bug"；重构敢动手。
**影响范围**：`common/` 两个大文件 + 所有 `@Inject('XxxRepo')` 调用点；需要测试兜底（T-2）。

### T-2 测试骨架 + CI　`P0`　`M`

**现状**：0 测试、0 CI。已有 493 行手工用例（`docs/AEG-测试用例.md`），说明业务规则是清楚的，只是没自动化。

**建议**：
- 第一层（优先）：API 集成测试，覆盖 6 条主链路 —— 登录鉴权、上传识别→核算、状态机非法跳转、删除约束、客户越权访问、文件归属校验。用 `supertest` + 测试库。
- 第二层：核算与 DI 计算的纯函数单测（金额与取整最容易错）。
- CI：GitHub Actions 跑 `typecheck + lint + test + build`，PR 必过。
- 不要追求覆盖率数字，先覆盖"错了会赔钱"的路径。

**收益**：后续 T-1、T-6 这类重构的前提；发布前的最后一道闸。
**影响范围**：仓库根 + api；不改进业务代码。

### T-3 文件存储外置　`P1`　`M`

**问题**：上传文件落 `apps/api/uploads/orderfiles`（本地磁盘），下载走 `res.sendFile`。单机够用，但备份、迁移、扩容都受制于这台机器；磁盘满会让整个上传功能挂掉。

**建议**：抽象 `StorageService`（`put/get/delete/signedUrl`），先实现本地驱动、再加 S3 兼容驱动（Cloudflare R2 / Backblaze 便宜且免出网费）；下载改签名 URL 直连，减少 API 带宽。

**收益**：扩容与迁移解耦；文件访问可审计。
**影响范围**：`order-files` / `image` / `license-upload` 三处上传点。

### T-4 可观测性　`P0`　`S`

**问题**：只有 `console.log`，没有请求日志、没有错误上报、没有健康探针。线上出问题只能靠"用户说打不开"。

**建议**：结构化日志（pino，带 `requestId`）+ 全局异常过滤器（统一错误响应，避免堆栈泄漏）+ `GET /api/health`（含 DB 连通与队列状态）+ 简单告警（进程守护 + 5xx 速率阈值发邮件/Telegram）。

**收益**：排障时间从小时级降到分钟级；也满足 PRD 里"加载失败不显示过期数据"的验收基础。
**影响范围**：`main.ts` + 全局过滤器；部署脚本加探针。

### T-5 登录安全加固　`P0`　`S`

**问题**：无频率限制（R3）、密码最短 6 位、JWT 12 小时不可撤销（R5）、CORS 默认 `*`（R4）。

**建议**：
- `@nestjs/throttler`：登录 5 次/分钟/IP，失败 10 次锁定 15 分钟（按用户名 + IP）。
- 密码策略提到 8 位且含字母与数字（存量账号下次改密时生效）。
- 生产环境启动时若 `CORS_ORIGIN` 未设置则**拒绝启动**（与 JWT 同样的强校验风格）。
- 配合 F-12 的 `token_version` 实现强制下线。

**收益**：堵住最容易被扫描器发现的三个口子。
**影响范围**：`main.ts`、`auth` 模块、`password-policy.ts`；部署 `.env` 需补 `CORS_ORIGIN`。

### T-6 前端共享层收敛　`P1`　`M`

**问题**：`packages/web-shared` 只有 193 行（auth/blob/errors/i18n/remember-password）。`ShipmentRouteMap`、`Layout`、`RequireAuth` 在各端各有一份，靠手工 `cp` 同步——本轮开发中已经手工同步过多次。

**建议**：把地图、布局、鉴权守卫、请求封装、i18n 初始化抽到 `web-shared`；词条按"通用 + 端专属"拆分，避免 738 条全量复制。

**收益**：改一处全端生效；四端视觉与交互不再漂移。
**影响范围**：4 个前端的 `components/`、`locales/`；需冒烟验证四端。

### T-7 前端数据层（引入 TanStack Query）　`P2`　`M`

**问题**：现状是 axios + zustand + 手写轮询（运营端 30 秒轮询船位、客户端 30 秒整页刷新）。轮询逻辑分散，无缓存去重、无失败重试策略，容易出现"切页面重复请求"。

**建议**：引入 TanStack Query 统一查询缓存、失效与轮询（`refetchInterval` + `refetchIntervalInBackground:false`），把现有手写 `setInterval` 收敛掉。

**收益**：代码量下降；切页不闪白；请求数下降（PRD 第 8 节"避免无意义重复请求"）。
**影响范围**：四端数据获取层，建议先在运营端试点。

### T-8 单机状态外置　`P1`　`M`

**问题**：AIS 轨迹在进程内存 + 本地 JSON；10 分钟扫描用进程内定时器；限流计数器也是进程内 Map（`inquiry.controller.ts:7`）。多实例即重复订阅、重复扫描。

**建议**：轨迹落 `ais_track_point` 表（已有 60 天/1000 点的清理规则，改成 DB 清理任务）；定时扫描改外部 cron 调受保护的内部接口，或用 PG advisory lock 保证单实例执行。

**收益**：具备水平扩容能力；重启不丢轨迹。
**影响范围**：`ais-stream.service.ts` + 1 张表 + 部署 cron。

### T-9 迁移与索引治理　`P1`　`S`

**问题**：两个迁移共用时间戳 `1762300000000`（R7）；`deal_status` 无索引（R8）。

**建议**：新增迁移把两者改名对齐（TypeORM 记录在 `migrations` 表里，改名需谨慎，可只对未来迁移严格编号）；补 `(client_id, deal_status)`、`(salesperson_id, status)` 复合索引，并用 `EXPLAIN ANALYZE` 验证列表查询。

**收益**：避免未来迁移顺序错乱；数据量增长后列表不退化。
**影响范围**：`migrations/` + 数据库。

### T-10 发布一致性　`P1`　`S`

**问题**：`versions.json` 显示 admin/customs 停在 11-13 的 `eef1d24`，api/ops/client 已到 11-16 的 `ab346cc`——说明上次发布只覆盖了部分端（R9）。

**建议**：`update.sh` 改为一次性构建并发布四端 + api；发布后脚本自动请求各端 `/api/version` 与 `versions.json` 比对，不一致直接告警。

**收益**：杜绝"前端调新接口 404"这类事故。
**影响范围**：`deploy/hostinger/update.sh` + 版本页。

### T-11 LGPD 与数据合规　`P2`　`M`

**问题**：客户证件照、CNPJ、联系人信息长期留存，无删除/导出机制，敏感字段未加密；审计日志存 PG 但可被直接修改。

**建议**：定数据保留期（如注销后 N 年删除）；提供客户数据导出与删除请求流程；证件照等敏感文件加密存储或至少限制下载审计；审计表追加哈希链（`prev_hash`）防篡改。

**收益**：面向巴西市场的合规底线；客户信任。
**影响范围**：client/profile + 存储层 + 审计。

### T-12 代码一致性与清理　`P2`　`S`

**问题**：根 `package.json` 有 `bcryptjs`，`apps/api` 又有 `bcrypt`（两者并存）；`mock-db.ts` 全量同步写盘；`output/`、`*.local.out.log` 等本地产物散在仓库根目录。

**建议**：统一用 `bcrypt`（Node 原生实现更快）；mock 写盘改防抖异步；把日志与临时产物纳入 `.gitignore`。

**收益**：减少"两个库同时存在"的困惑；仓库干净。
**影响范围**：依赖与少量工具函数。

## 七、建议路线图

**阶段一 · 止血（约 2 周）**
T-2 CI + 测试骨架 → T-5 登录加固 → T-4 日志与探针 → F-3 客户确认 → F-4 节点编辑 → F-12 员工改密。
这一阶段不改数据模型，风险可控，但把"会不会出事"和"最影响成交的两个小功能"一起解决。

**阶段二 · 客户闭环（约 4-6 周）**
F-1 通知 → F-2 PDF → F-6 单证清单 → T-3 存储外置 → T-10 发布一致性 → T-9 索引治理。
完成后客户的完整体验是：提交 → 收到"报价已出"邮件 → 下载 PDF → 在线接受 → 收到节点更新 → 下载单证。

**阶段三 · 结构化重构与规模化（1 个季度）**
T-1 数据层收敛 → T-8 状态外置 → T-6 共享层 → T-7 查询层 → F-10 看板 / F-8 账龄 / F-9 汇率损益。
这一阶段的前置条件是测试覆盖到位，否则不建议动数据层。

**按需启动**
F-13 AIS 商业源（先测算单票成本）、F-14 移动端、T-11 LGPD、F-11 询盘落库（如果想马上多一些线索，F-11 可以提前到阶段二，成本仅 S）。
